📈 Strategic Overview & Business Value
In Southeast Asia, and particularly in Thailand, LINE is more than a chat application—it is the central operating system of daily life. For businesses running Odoo ERP, requiring customers or operational staff to log in to complex web portals or download dedicated mobile apps introduces massive friction, cart abandonment, and delayed sales cycles.

Odie Flow is a state-of-the-art conversational commerce system that bridges this gap. It enables customers, field agents, and warehouse operators to run core Odoo operations directly inside LINE Official Account (OA), powered by an intelligent, natural-language AI agent (Nong Sora - น้องโซระ) built on Google Vertex AI.

🏗️ Technical Architecture & System Topography
Odie Flow is built on a highly scalable, serverless, and secure stack on Google Cloud Platform (GCP) integrated with Odoo's XML-RPC / JSON-RPC API.

Mermaid diagram
🛠️ Core Technology Stack
Frontend Interface: LINE Web Client & Native App (utilizing LINE Flex Messages for premium, customized card UIs).
Application Gateway: Node.js & TypeScript Express Server deployed on Google Cloud Run (Stateless, autoscaling to zero when idle for ultra-cost-efficiency).
Intelligence Engine: Vertex AI (Gemini 1.5/2.0) executing structured tool-use / function-calling, and custom zero-shot Intent Classification.
Database & Session State: Google Cloud Firestore to track real-time chat histories, language selections, and VIP engagement scoring.
Cohort & Data Warehouse: Google BigQuery syncs e-commerce behavior to build segmentation cohorts (VIP, Cart Abandoners, Dormant).
Enterprise Core: Odoo ERP (Community or Enterprise) linked over secure JSON-RPC for Sales Order, Quotation, CRM, and Stock controls.

📦 Workflow 3: Live Order & Quotation Tracking
Customers track their shipments, quotes, and fulfillment milestones in real-time, drastically reducing support requests.

Trigger: Customer texts "DEMO ORDER SO0023" or asks "Where is my order?"
Execution:
Gemini extracts the order reference (SO0023).
Odie Server queries Odoo's sale.order model.

Delivers an elegant progress tracker timeline card via LINE.
🚨 Workflow 4: Smart Agent Escalation
When customer queries become overly complex, or if sentiment analysis indicates user frustration, Odie Flow smoothly transitions the chat to a human operator.

IMPORTANT

Escalation Mechanism:

Gemini calls escalateToHuman(reason).
The system sets isEscalated = true and logs the escalationReason in the user's Firestore document.
Future messages bypass the AI completely and are routed to an admin desk.
The bot politely tells the customer: "Spoke to an agent. Our team will contact you shortly."
📊 Workflow 5: AI Daily Sales & Stock Reports (Admin On-The-Go)
For managers and directors, keeping tabs on business health doesn't require logging into a computer. They receive beautiful, AI-summarized executive reports in their LINE app.

How it works:
A cron job (or admin command DEMO REPORT) retrieves yesterday's sales orders and product inventory from Odoo.
Odie compiles the raw data and sends it to Vertex AI (Gemini).
Gemini analyses top-selling items, detects inventory warnings (low stock alerts), and writes a highly polished, professional executive summary in Thai.
The summary is formatted into a custom Admin Dashboard Flex Message and sent directly to the admin's LINE.

🔒 Security, Compliance & Enterprise Readiness
Odie Flow is designed with multi-layered, enterprise-grade safety protocols:

LINE Signature Validation: Every webhook request validates the X-Line-Signature header using HMAC-SHA256 and the LINE_CHANNEL_SECRET to prevent spoofing.
Stateless IAM Authentication: Express server running on GCP Cloud Run uses Application Default Credentials (ADC) to securely connect to Firestore, BigQuery, and Vertex AI without storing hardcoded GCP credential keys.
Encrypted Odoo ERP Access: Calls are made over secure HTTPS JSON-RPC utilizing Odoo user API keys (recommending restricted, role-based service accounts within Odoo).

## Phase 1-7 Implementation Roadmap

This roadmap delivers two outcomes in parallel:
1. Production-grade stability and security.
2. A unique market feature: Thai Group-Buy Negotiation Engine on LINE + Odoo.

### Phase 1: Security Baseline and Attack Surface Reduction (Week 1)
Goal: remove easy abuse paths and harden public endpoints.

Step-by-step:
1. Protect operational routes with admin token middleware for /jobs/daily-report, /jobs/segmentation, and /jobs/seed-odoo.
2. Keep /webhook-test disabled in production by default and require strong token verification when explicitly enabled.
3. Add per-route rate limits for /webhook and /webhook-test.
4. Add JSON payload size limits and reject oversized requests.
5. Redact message text and phone-like values in logs for production.

Definition of done:
1. All sensitive routes return 401 without token.
2. Abuse simulation cannot flood endpoints beyond configured limits.
3. Security checklist passes in staging.

### Phase 2: Reliability, Readiness, and Observability (Week 2)
Goal: ensure stable behavior under transient failures and make incidents diagnosable fast.

Step-by-step:
1. Upgrade readiness endpoint to validate Firestore and Odoo connectivity with short timeout.
2. Implement structured logging with correlation id per request.
3. Add retry with exponential backoff and timeout for safe Odoo read operations.
4. Keep write operations single-attempt, but return explicit error and audit events.
5. Add alert thresholds for error rate, latency, and webhook failure spikes.

Definition of done:
1. P95 webhook latency and failure rates are visible in logs/metrics.
2. Dependency outage is reflected by readiness status.
3. Incident triage can identify root cause within minutes.

### Phase 3: Data Model for Thai Group-Buy (Week 3)
Goal: establish session lifecycle and participant ledger for group-buy.

Step-by-step:
1. Create Firestore collections: group_buy_sessions, group_buy_participants, group_buy_events.
2. Define session states: draft, active, locked, closed, expired, cancelled.
3. Add participant constraints: min qty, max qty per user, join cooldown.
4. Add tier-pricing fields and recalculation rules on every join.
5. Store audit events for every state transition.

Definition of done:
1. Session and participant records are created and updated deterministically.
2. Event log supports replay and reconciliation.

### Phase 4: LINE Command and Experience Layer (Week 4)
Goal: release first usable LINE-native group-buy experience.

Step-by-step:
1. Add commands:
       - START GROUPBUY <product>,<targetQty>,<hours>
       - JOIN GROUPBUY <sessionId>,<qty>
       - STATUS GROUPBUY <sessionId>
       - CONFIRM GROUPBUY <sessionId>
       - CANCEL GROUPBUY <sessionId>
2. Add strict command payload validation with clear bilingual error messages.
3. Build Flex templates for progress bar, pledged quantity, next price tier, and countdown.
4. Broadcast session updates to participants on each state/pricing change.
5. Add admin override commands for forced close/cancel.

Definition of done:
1. Users can complete full group-buy flow inside LINE without web UI.
2. Error messages remain clear in Thai and English.

### Phase 5: Odoo Commercial Realization (Week 5)
Goal: convert successful group-buy sessions into real Odoo business objects.

Step-by-step:
1. On CONFIRM, resolve participant identities to Odoo partners.
2. Create quotation/order references with group-buy session id linkage.
3. Write back Odoo ids to Firestore for traceability.
4. Add compensating action path for partial failures (retry queue + manual review state).
5. Generate participant-level summary message: unit price, quantity, total, reference id.

Definition of done:
1. End-to-end trace exists from LINE session to Odoo document ids.
2. Partial failures are recoverable without silent data loss.

### Phase 6: Payments, Quality Gates, and Controlled Beta (Week 6-7)
Goal: prepare real-world transactions and protect quality before broad release.

Step-by-step:
1. Add payment status workflow: pending, paid, expired, refunded.
2. Implement PromptPay-ready abstraction (manual mark-paid allowed for beta).
3. Add automated tests for parser, state transitions, authorization, and Odoo integration mocks.
4. Run load tests for burst traffic and rate-limit behavior.
5. Beta rollout to internal users and a small pilot merchant cohort.

Definition of done:
1. Critical paths covered by automated tests.
2. Beta users complete transactions with tracked success metrics.

### Phase 7: Production Launch, Scale, and Optimization (Week 8+)
Goal: launch safely, scale gradually, and optimize for conversion and retention.

Step-by-step:
1. Enable feature flags for staged rollout: 10%, 30%, 100%.
2. Track KPI dashboard:
       - Group-buy completion rate
       - Average order value uplift
       - Payment completion rate
       - Repeat participation rate
3. Run A/B tests on message copy, urgency cues, and tier display.
4. Add anti-abuse scoring for repeated spam joins/cancels.
5. Publish operations playbook for support, rollback, and reconciliation.

Definition of done:
1. Stable launch with rollback readiness.
2. KPI targets are measurable and improving week over week.
